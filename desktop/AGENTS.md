# Mux Deck v2 开发约定

## 适用范围

本文件及 `docs/agents/` 只约束 `desktop/` 下的 C#/.NET/Avalonia 新版。仓库外层的 Python/Web 代码属于 v1，作为业务参考；v1 的架构冻结约束不作为 v2 的代码骨架。

当前阶段、顺序与完成条件以[开发流程](docs/agents/migration.md#当前进度)为准，本文不重复阶段内容。功能完成以对应阶段验收为准；窗口可显示和代码可构建不代表功能已完成。

## 按任务读取

- **代码变更**：在新增、修改、移动或删除代码前，读取 [代码骨架](docs/agents/skeleton.md)，先确定代码所属层（Domain / Application / Infrastructure / Desktop）、依赖方向、契约和文件归属；迁移期间新代码按骨架的过渡规则落位。
- **结构决策**：新增或拆分项目、改变依赖方向、拆分 Contracts 时，先读取 [ADR](docs/adr/)。按已接受的 ADR 实施时只需在提交与 PR 中引用，不修订 ADR；超出已接受 ADR 的结构变更，先新增或修订 ADR 并经用户确认，再改骨架与代码。
- **进行中的任务**：开始前查看 [任务文档](docs/tasks/) 中对应的文件，按其范围与粒度实施；架构分层重构按 [任务计划](docs/tasks/arch-layering.md) 逐 PR 执行。
- **功能开发**：读取 [开发流程](docs/agents/migration.md)，确认当前阶段、输入输出、范围和完成条件；涉及旧版行为时核对对应旧代码。
- **验证与交付**：读取 [验证要求](docs/agents/verification.md)，按改动选择检查并记录结果。
- **工具诊断**：解析、修改或验收外部工具输出、告警或失败策略时，读取 [工具诊断分类](docs/agents/diagnostics.md)；该文档维护唯一分类白名单与未知诊断策略。
- **运行与依赖**：命令见 [README](README.md)；SDK、框架和包版本以项目配置及锁文件为准。

## 工作约定

- 每次开发先写清本次输入、输出、失败行为和验收场景，再实现该范围内的完整流程。长期规则放在对应规范；阶段进度放在 `migration.md`；单项任务的计划与实施记录放在 `docs/tasks/`。
- 新版直接执行 C# 核心流程。v1 可用于阅读和行为对照，不作为新版的 HTTP 或 Python 业务服务。
- 功能迁移区分保留行为、修正缺陷和新增能力；发现旧版缺陷时记录差异与验证依据。
- 一次改动只做一类事：搬迁/重构、缺陷修复与新增能力分开提交，便于对照验证。
- 依赖方向以架构测试为准。测试失败时修正代码，不通过放宽测试绕过；确需改变规则时先修订 ADR 与骨架。
- 每条规则只保留一个权威位置；改变规则时同步调整它的链接和相关实现。
- 新增或修改的代码注释使用中文，解释原因、约束和异常路径。
- 子代理按实际需要使用；按任务文档的 PR 粒度分派，任务同时说明范围、共享文件归属和验收结果；`MuxDeck.sln`、`packages.lock.json`、`Directory.Build.props` 与 `docs/agents/` 同一时间只由一个代理修改。

## 提交与分支

- 提交信息使用 `类型(desktop): 摘要`（如 `feat`、`fix`、`refactor`、`docs`、`test`），正文说明原因、改动范围和 `Validation:`（实际命令与通过计数）。
- 代码改动在 `v2/<主题>` 分支完成，经 PR 合并到 `v2/avalonia-rewrite`；CI 通过后再合并。

## 完成报告

说明实际完成的能力、执行的验证和仍未覆盖的场景，并更新对应任务文档的实施结果。真实工具链尚未通过时，明确标为未验收；涉及项目结构或依赖时同时说明架构测试结果。
